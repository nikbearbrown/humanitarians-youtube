## This week's contribution

**Question.** How does pitch-correction software find the note a singer sang and move it to the right one?

**Prediction.** No prediction was written down before the build. The working assumption going in was that the hard,
robotic sound comes from the correction itself (the shifting), not from how fast it is applied.

**What I built/tried.** `autotune.py`: a synthetic singer (a buzzing source shaped by "ah" vowel resonances) sings an
original seven-note phrase in C major, off-key on purpose (scoops, vibrato, drift). A YIN detector finds the pitch every
5 ms and is scored against the true pitch; a corrector snaps each moment to the nearest note of C major at two retune
speeds (60 ms and 0 ms) and applies it to the audio with TD-PSOLA, using only the detected pitch; the corrected audio is
measured again. A held note is also moved up 4 semitones by plain resampling, by the patent's resample-and-repeat-cycles
method, and by PSOLA. The six body scenes are three.js stages in HyperFrames (`build_hf.py`, `hyperframes/scenes/`).

**Observed result.** The detector was within 5 cents of the true pitch in 93.1% of 692 sung frames (11 misses, all
within 11 ms of a note's start). As sung, the take averaged 29.1 cents off and sat within 5 cents of a note 4.5% of the
time. At 60 ms it averaged 6.5 cents off with the vibrato kept (about ±14 cents); at 0 ms it sat within 5 cents of a
note 90.6% of the time. The same correction at a different speed made the difference, so the assumption was wrong.
Moving the held note up 4 semitones moved the vowel +25.8% by resampling (and shortened it to 1.27 s), +27.8% by the
patent's method (length kept), and +0.6% by PSOLA.

**Next experiment.** Run the same corrector on a real recorded voice, and add a formant-preserving option to the
patent's method to see how close it gets to PSOLA.

Memory API — Medhavy Hub

A student spends a semester in one textbook. The tutor learns how they think.
Next semester they open a different book, and the tutor there has never heard
of them. The Memory API is the part of the Medhavy hub built to fix that — two
endpoints, two tables, and one string that decides whether two books are
talking about the same student.

WHAT YOU WILL KNOW AFTER WATCHING
Why there are two tables and not one — a transcript is what was said, a profile
is what the tutor concluded. What memory_subject is, and why a naming
convention with no identity resolution behind it is the entire cross-book
mechanism. Why short-term memory is a rolling window and not an archive. And
the honest part: the hub provides all of this, but at least one textbook still
keeps memory in local SQLite, so the machinery is built and waiting rather than
live.

A NOTE ON ACCURACY
Every claim here was checked against the medhavi-hub source after filming. Two
corrections worth stating up front: the 24-turn / 48-row window is the default
of a caller-supplied parameter, not a fixed limit — a textbook backend can ask
for up to 100 turns. And while the endpoints do use shared-secret auth, that
check is skipped entirely in non-production when the secret is unset. Full
verification trail, including the confirmation that no textbook currently calls
the hub, is published with the source package.

# FACTCHECK - How Database Indexing Searches Millions of Records in Milliseconds

| Claim | Source / Technical Standard | Verdict | Implementation Note |
|---|---|---|---|
| Unindexed queries force full table scans with O(N) disk reads | Database System Concepts (Silberschatz, Korth, Sudarshan); PostgreSQL / MySQL internals | TRUE | Without an index, the storage manager must sequentially inspect every page/block from the physical data files to evaluate WHERE clauses. |
| B-Tree / B+Tree indexes reduce lookup complexity to O(log N) | Knuth, The Art of Computer Programming, Vol. 3 (Sorting and Searching); Bayer & McCreight (1972) | TRUE | Multi-way balanced search trees maintain sorted keys across pages, bounding the height of the tree typically to 3 to 4 levels for hundreds of millions of keys. |
| Tree traversal navigates from root through branch pages in 3-4 I/O hops | Designing Data-Intensive Applications (Kleppmann, Ch. 3); PostgreSQL B-Tree Index Implementation | TRUE | High branching factor (fanout 100-500 keys per 8KB page) ensures 3-4 page reads locate any record among millions of rows. |
| Doubly linked leaf nodes enable fast range scans without re-traversal | Comer, "The Ubiquitous B-Tree" (ACM Computing Surveys, 1979); SQLite / InnoDB B+Tree architecture | TRUE | In a B+Tree, leaf nodes are linked sequentially forward and backward, allowing range scans (e.g., BETWEEN x AND y) to follow leaf chains sequentially. |
| Clustered index physically sorts data rows; secondary index references primary key | MySQL InnoDB Architecture Guide; Microsoft SQL Server Clustered Index Architecture | TRUE | InnoDB tables are clustered by primary key; secondary index leaves contain secondary key values and primary key values for row pointer lookups. |
| Composite indexes obey the leftmost prefix rule | Oracle Database SQL Tuning Guide; MySQL Composite Index Optimization | TRUE | Composite index (A, B, C) can satisfy queries filtering on (A), (A, B), or (A, B, C), but cannot utilize the index for filtering on (B, C) alone. |
| Write operations incur maintenance penalty due to index node splits and page updates | Hellerstein, Stonebraker, Hamilton, "Architecture of a Database System" (Foundations and Trends in Databases) | TRUE | Every INSERT, UPDATE of indexed columns, and DELETE requires updating all corresponding index trees, triggering page splits and I/O writes. |
| Covering indexes satisfy queries entirely from leaf pages without table lookups | PostgreSQL Index-Only Scans Documentation; MySQL Using Index Optimization | TRUE | When an index contains all columns requested in SELECT and WHERE clauses, the query engine performs an index-only scan, bypassing heap table I/O completely. |

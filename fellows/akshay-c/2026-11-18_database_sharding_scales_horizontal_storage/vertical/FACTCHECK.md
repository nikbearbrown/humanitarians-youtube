# FACTCHECK - How Database Sharding Scales Horizontal Storage

| Claim | Source / Technical Standard | Verdict | Implementation Note |
|---|---|---|---|
| Monolithic databases hit vertical scaling ceilings when datasets exceed single-machine RAM, CPU, and IOPS | Stonebraker et al., "The End of an Architectural Era" (VLDB 2007); Designing Data-Intensive Applications (Kleppmann, Ch. 6) | TRUE | Vertical scaling (bigger CPU, more RAM, NVMe arrays) faces steep cost curves and physical hardware limits. Single-node write locks, index tree traversal depth, and connection limits exhaust capacity at high scale. |
| Database sharding partitions datasets horizontally across independent nodes with dedicated resources | Codd (1970); Stonebraker (Shared-Nothing Architecture, 1986); Google Spanner & Citus Data Documentation | TRUE | In a shared-nothing sharded architecture, each shard operates as an autonomous database with its own independent memory, CPU, and disk storage, eliminating hardware contention. |
| Shard keys determine data placement across physical nodes | Designing Data-Intensive Applications (Kleppmann, 2017); MongoDB Sharding Architecture Guide | TRUE | The shard key (e.g. `user_id`, `tenant_id`) is evaluated by the routing logic to direct write and read operations to the specific partition hosting that key. |
| Range partitioning groups contiguous values, while hash partitioning distributes writes uniformly | MySQL Cluster / Vitess Architecture; CockroachDB Architecture Whitepaper | TRUE | Range partitioning enables fast range scans (`BETWEEN X AND Y`) but risks hot spots on sequential auto-increment keys. Hash partitioning (`hash(key) % N` or consistent hashing) disperses data uniformly to avoid write hot spots. |
| Query routers direct queries containing shard keys to single shards with zero cross-talk | Vitess (VTGate coordinator); MongoDB (mongos router); Citus/PostgreSQL Distributed Query Engine | TRUE | When a query includes the partition key in its `WHERE` clause, the router calculates the exact shard location and forwards the query directly, achieving single-millisecond latency. |
| Queries lacking shard keys require scatter-gather execution with high latency overhead | Designing Data-Intensive Applications (Kleppmann, Ch. 6); Vitess Distributed Execution Docs | TRUE | Without a shard key, the coordinator must broadcast the query in parallel to all $N$ shards, wait for all partial responses, and sort/merge/aggregate them in memory, multiplying network latency and resource load. |
| Hot shards require partition splitting and rebalancing without downtime | Vitess Resharding VExec; DynamoDB Partition Splits; Google Bigtable Paper (Chang et al., 2006) | TRUE | When a shard reaches storage or throughput limits, systems split the partition range and stream historical data plus live CDC changes to new hardware, switching traffic atomically. |
| High availability in production pairs each shard with independent primary-replica sets | AWS Aurora Multi-Master / Multi-AZ; Vitess Shard High Availability; MongoDB Replica Sets | TRUE | Individual shards are never single points of failure. Each shard runs a primary for writes alongside synchronous or asynchronous replicas for failover and read scaling. |

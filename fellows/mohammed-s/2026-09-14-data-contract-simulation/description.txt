Prove The Number Changed — Catching Schema Breaks That Compile Clean

A backend engineer renames a column from amount_cents to amount and divides by a
hundred to match. Nothing crashes. Every dbt model still compiles. Every test
still passes. And monthly recurring revenue is now a hundred times too low.

This is the build reel for the layer I added to my data contract agent to catch
exactly that: instead of warning that a metric "may be wrong", it stands up a
throwaway DuckDB warehouse, materializes the whole dbt DAG straight from the
manifest, replays the migration, rebuilds, and diffs the marts. The warning is a
number now, not a hunch.

The interesting part is why it has to build TWICE. Replaying the migration just
makes every model that reads the dropped column fail to compile — the loud half,
which the deterministic layer already proved. But nobody merges a red pipeline: a
reviewer renames the column in the staging model and moves on, and *that* is the
state in which the number is silently wrong. So pass one records what breaks, and
pass two applies the mechanical fix a reviewer would apply — scoped by lineage,
not by name — and measures from there.

------------------------------------------------------------------------------
PART 1 -- Same sentence, embedded by both models: how similar are the
          two resulting vectors to EACH OTHER (cross-model, same text)?
------------------------------------------------------------------------------
Mean cosine similarity between Model-A and Model-B vectors of the IDENTICAL sentence, averaged over all 10 corpus docs: 0.7416
  (min 0.6832, max 0.7801)
If cross-model vectors lived in a shared, comparable geometry, this should be very high (close to the same-model self-similarity of 1.0, since it's the exact same text). Instead it's far from 1.0 -- the two models place even IDENTICAL text in incompatible regions of two different vector spaces.

PART 3 SUMMARY
------------------------------------------------------------------------------
Top-1 retrieval accuracy, CLEAN (same-model) index: 3/3
Top-1 retrieval accuracy, STALE/MIXED (cross-model) index: 3/3
HONEST NOTE on this corpus: top-1 accuracy held at 3/3 in both conditions above --
this 10-sentence corpus spans topics distinct enough that the correct answer's
similarity margin over the next-best wrong answer (commonly 0.3-0.6) is larger than
the cross-model degradation this run measured (roughly a 0.08-0.14 absolute drop in
cosine similarity for a stale doc, consistent with Part 1/2's numbers above). The
similarity SCORES are genuinely, measurably degraded by staleness in every case above
(e.g. Q1 doc[1]: 0.6839 -> 0.5897; Q2 doc[6]: 0.7774 -> 0.6420) even though the ranking
survived this particular corpus's wide topic margins. Part 4 below finds a real,
reproducible case -- still real models, real embeddings, no fabricated numbers -- where
two genuinely close, confusable documents exist, and the SAME mechanism demonstrated
above (staleness suppressing a doc's effective similarity) is enough to flip which one
wins the ranking: the exact silent failure this video is about.

==============================================================================
PART 4 -- A genuine top-1 RANK INVERSION, found on a closer, more confusable pair
==============================================================================
Two near-duplicate-topic documents, deliberately close enough to be a real
retrieval contest (not two totally unrelated sentences):
  doc[CORRECT]: "Our refund policy gives you your money back in cash within thirty days of purchase with a receipt."
  doc[DISTRACTOR]: "Returns on sale items are only accepted for store credit, not a refund."
  Query: "Can I get cash back for a return, or only credit?"
  Scenario: doc[CORRECT] was indexed with Model A originally and NEVER re-embedded
  after the app switched to Model B; doc[DISTRACTOR] was added later and IS a fresh
  Model-B vector (the realistic shape of a real partial migration). The query is
  embedded with Model B, since that's what the live app calls today.

  CLEAN index (both docs embedded with Model B, same-model search):
    doc[CORRECT]    sim=+0.6090
    doc[DISTRACTOR] sim=+0.5859
    -> top-1: doc[CORRECT] (right answer)
  STALE/MIXED index (doc[CORRECT] still in Model-A space, never re-embedded):
    doc[CORRECT]    sim=+0.5109  (same document, same query -- only its
                                   embedding model changed between these two lines)
    doc[DISTRACTOR] sim=+0.5859  (unchanged -- it's fresh Model-B both times)
    -> top-1: doc[DISTRACTOR] (WRONG)

  RESULT: a genuine rank inversion. The same two real documents and the same real
  query; the ONLY variable that changed between the clean and stale runs is which
  embedding model produced doc[CORRECT]'s stored vector. In the clean index the
  right document wins. In the stale/mixed index -- the realistic state of a vector
  store that was partially migrated to a new embedding model -- the WRONG document
  wins instead, silently, with no error, no warning, and no change to the query or
  the retrieval code itself.

This run used two real, different, published sentence-transformer checkpoints and real mean-pooled, L2-normalized embeddings computed in this script -- every number above, in all 4 parts, came from this exact run, not from a hypothetical or hand-typed example.

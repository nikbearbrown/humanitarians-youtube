Should a company keep its code in one repository, or many? This explainer compares monorepos and polyrepos.

What's covered:
- Polyrepo: one repository per project, with independence and clear ownership
- Monorepo: everything in one repository, one history, one toolset
- One commit can update a library and every project that uses it
- At huge scale, plain checkouts and builds crawl without special tooling
- Sparse checkout downloads only what you need; remote caching reuses earlier builds
- No universal winner: it's independence versus tight coordination

Sources: Google's 2015 description of its monorepo, git sparse-checkout documentation, Bazel remote caching documentation. File counts and cache results come from a real toy repo; build-time bars are illustrative.

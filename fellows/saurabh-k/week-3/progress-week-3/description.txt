Repo Sensei, Week Three — an AI that has to show you where it looked

You join a codebase with a hundred thousand lines in it and you have one question:
where does this feature actually live? Ask an assistant and you usually get a fluent
paragraph with nothing underneath it you can open.

Repo Sensei is what I am building instead. It indexes a repository first, and every
answer it gives has to come back carrying the file and the lines it came from.

What's in this one:
— The four stages: clone, parse, index, and only then answer.
— Why it parses instead of grepping. It uses tree-sitter, the same parser your editor
  uses, so a function is seen as a function rather than matched as text.
— Eighteen query files covering definitions, calls, imports and references, across
  Python, TypeScript and JavaScript.
— What a trace is: one feature followed from the button a user clicks, through the API
  that handles it, down to the table it writes.
— Where it stands after nine days, measured rather than estimated: 101,318 lines of
  Python and TypeScript, 770 files across apps, packages and workers, 132 test files,
  179 commits since 17 October.
— The honest part: indexing works, answering is still being built, and there is no demo
  here of something that does not exist yet.

The rule the whole project runs on: an answer you cannot check is not an answer. In code
that matters more than anywhere else, because a confident wrong answer gets reviewed,
approved and shipped.

Your turn: next time an assistant explains your own codebase back to you, ask it which
file and which line. Then open that file and look.

# CARRY-OUT — GATE C

Written before any other narration. Every beat exists to make this sentence
survivable.

## The line

> **A Skill isn't installed software — it's a file Claude reads before it
> acts. Same request gets the same steps every time, but only for what
> that file actually wrote down.**

## The wrong guess it defeats

That `cowork-plugin-customizer` — a name with "plugin" sitting right in the
middle of it — is a plugin Claude has installed, the way an app installs a
feature that then runs on its own. It isn't. It's a folder containing a
`SKILL.md`: plain-language instructions that Claude opens and reads before
doing anything. The file is the program.

## The secondhand test

*If someone repeats only this sentence in a meeting next week, is it still
true?*

Yes — it compresses the one distinction that matters (read, not installed)
and the one limit that matters (scoped to what's written), without needing
a second sentence for either.

## What it deliberately does not say

- **Not what `cowork-plugin-customizer` specifically does step by step.**
  The source batch-build left this detail as an unfilled `>` placeholder in
  four separate beats (B00, B03, BVDT, BHTF) and the real `SKILL.md` lives
  only on a machine this workspace can't reach. The one fact the source
  states outright — "customize a Claude Code plugin for a specific
  organization's tools" — is kept as the anchor; nothing about *how* it does
  that is invented.
- **Not a verdict on the skill's design.** The source's B03/BVDT framed
  "what it gets right" / "what it bites" as a Teardown judgment. Plain keeps
  the same underlying mechanism fact (repeatable within scope, silent past
  it) but states it as a boundary, not a critique.
- **Not that Claude refuses or errors past the file's scope.** Going beyond
  what a Skill's Steps section covers doesn't break anything — Claude just
  stops following that skill's specific procedure and falls back to its own
  general judgment. That's a different mode, not a failure.

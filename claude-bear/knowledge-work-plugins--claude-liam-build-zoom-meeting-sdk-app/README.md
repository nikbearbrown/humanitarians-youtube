# It Doesn't Design the App. It Follows the File.

**Channel:** @HumanitariansAI
**Playlist:** Extending Claude — Skills, Plugins & Connectors

## Description

When Claude builds a Zoom meeting into an app, does it design that
integration on its own, or is it following a file that already has the
platform's rules written down?

This is Professor Bear's Claude-basics series, narrated by Liam. Today's
worked example is `build-zoom-meeting-sdk-app`, an Anthropic Claude Skill
from a Zoom partner-built plugin. A Skill is a folder Claude reads before
it acts — here, a `RUNBOOK.md` and a `SKILL.md`, plus one folder per
platform (android, electron, iOS, Linux, macOS, react-native). The
instructions run as steps, in order: read the file, execute each step,
return the result. `build-zoom-meeting-sdk-app`'s specific job is
narrower than its name suggests — it's a reference, not a
decision-maker. It's read only after a build has already been routed to
a meeting-embed workflow, and it supplies that platform's exact rules:
real meeting joins, auth and join flows, waiting-room handling,
meeting-bot patterns. It doesn't choose the platform or decide to embed a
meeting at all. It supplies the rules for the one already chosen.

Carry-out: build-zoom-meeting-sdk-app never decides to build a Zoom
integration — it hands Claude the platform's exact join rules once that
decision's already made.
